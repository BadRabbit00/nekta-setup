# Диски: разметка, RAID и монтирование

## Что требует вендор

Диск 2 (хранение) на сервере Nekta монтируется **именно в `/nekta`** — путь
зашит в установщик вендора. Роль `requirements` прерывает выполнение, если
`/nekta` не смонтирован отдельным томом.

На сервере копий диск 2 — **RAID1 из двух HDD**.

## Указывайте диски по by-id, а не по /dev/sdX

`/dev/sdb` — не свойство диска, а порядок, в котором ядро его увидело. После
замены диска, добавления контроллера или простой перезагрузки `sdb` и `sdc`
меняются местами. Для RAID и тома данных это означает разметку не того диска.

```bash
# на целевом сервере
lsblk -o NAME,SIZE,TYPE,FSTYPE,SERIAL,MOUNTPOINT
ls -l /dev/disk/by-id/ | grep -v part
```

`inventory/host_vars/nekta-01.yml`:

```yaml
storage_volumes:
  - device: "/dev/disk/by-id/ata-ST4000NM000A-2HZ100_WJG0ABCD"
    mountpoint: "/nekta"
    fstype: "ext4"
    opts: "defaults,noatime"
    label: "nekta-data"
```

В `/etc/fstab` роль всё равно запишет UUID — он переживает и переименование
устройства, и пересборку массива.

## Предохранитель от переформатирования

Роль `storage` **не создаёт файловую систему**, если на устройстве уже что-то
есть, и не собирает RAID из дисков с данными. Вместо этого выполнение
прерывается:

```
На /dev/sdb обнаружено 'LVM2_member'. Роль не будет затирать существующие
данные. Если диск действительно пустой, запустите с -e storage_force_format=true
```

Это защищает от самой дорогой ошибки в таких плейбуках — запуска на сервере,
где данные уже есть. Снимать предохранитель нужно осознанно и только для
конкретного прогона:

```bash
ansible-playbook playbooks/nekta.yml --tags storage -e storage_force_format=true
```

## RAID1 на сервере копий

```yaml
storage_raid_create: true
storage_raid_arrays:
  - name: "/dev/md0"
    level: 1
    devices:
      - "/dev/disk/by-id/ata-HDD_SERIAL_1"
      - "/dev/disk/by-id/ata-HDD_SERIAL_2"
```

Роль создаёт массив, **записывает его состав в `/etc/mdadm/mdadm.conf` и
пересобирает initramfs**. Без этого после перезагрузки массив может собраться
под именем `/dev/md127`, и том из `fstab` не смонтируется — сервер поднимется без хранилища,
а запись пойдёт в корневой раздел. Именно поэтому монтирование идёт по UUID,
а не по имени устройства.

Пропущенные записи выявятся сразу:

```bash
cat /proc/mdstat
mdadm --detail /dev/md0
findmnt /backup
```

### Контроль состояния массива

Роль записывает `MAILADDR` в `mdadm.conf` и включает службу `mdmonitor`.
Письма о деградации массива уйдут только при настроенном почтовом агенте —
плейбуки его не устанавливают (см. [00-scope.md](00-scope.md)), поэтому
проверьте отправку отдельно:

```bash
mdadm --monitor --scan --test --oneshot
```

Раз в месяц Debian/Ubuntu штатно запускают проверку целостности массива
(`/etc/cron.d/mdadm`). Не отключайте её: тихо испортившийся сектор на втором
диске обнаруживается только при чтении, то есть в худшем случае — при
восстановлении.

## Файловые системы

По умолчанию `ext4`. Резерв суперпользователя остаётся системным (5%): в документации Nekta про
него ничего нет. На диске 4 ТБ это 200 ГБ, которые никто не использует, —
если хотите их вернуть, поставьте `storage_reserved_blocks_percentage: 1`.

`xfs` тоже поддерживается (`fstype: "xfs"`) и лучше держит очень большие
файлы, но не умеет уменьшаться. Для тома под многолетний архив показаний
разница невелика; менять умолчание есть смысл только под конкретный профиль
нагрузки.

## S.M.A.R.T.

Контроль состояния дисков плейбуками не настраивается — в документации Nekta
его нет. Если решите добавить, потребуется пакет `smartmontools`; на сервере
Nekta ставьте его после установки стека вендором.
