# Резервное копирование и восстановление

## Как это устроено

Копии **забирает** сервер резервного копирования (pull-модель), а не отдаёт
сервер Nekta. Это принципиально: у сервера Nekta нет ни доступа к хранилищу,
ни прав на удаление снимков, поэтому его отказ, ошибка администратора или
компрометация не уносят архив вместе с оригиналом.

Один цикл:

```
backup-01                                          nekta-01
   │  1. ssh sudo nekta-predump ───────────────────►  дампы СУБД из контейнеров
   │                                                  в /nekta/backup-dumps
   │  2. rsync --link-dest ◄─────────────────────────  /nekta /etc /root
   │     новый каталог-снимок; неизменившиеся файлы
   │     становятся жёсткими ссылками на предыдущий
   │  3. (опционально) borg create — архив с дедупликацией
   │  4. прореживание по схеме дед-отец-сын
   │  5. запись состояния для мониторинга
```

### Почему сначала дампы, а потом файлы

Побайтовое копирование работающей СУБД даёт несогласованный снимок: файлы
данных, журналы и индексы попадают в копию в разные моменты времени.
Восстановление из такого снимка в лучшем случае требует отката журнала, в
худшем — не проходит вообще.

`nekta-predump` на сервере Nekta находит контейнеры с PostgreSQL, MongoDB,
MySQL/MariaDB и ClickHouse и снимает логические дампы штатными средствами
самих СУБД. Rsync забирает уже готовые файлы. Заодно сохраняется состояние
системы — список контейнеров, образов, томов, пакетов, сетевых настроек и
разметки дисков: при восстановлении на новом железе это экономит часы.

Если стек ещё не установлен, шаг пропускается с записью в журнал.

### Почему снимки на жёстких ссылках

Каждый снимок — полноценное дерево файлов: восстановление это обычный `cp`,
без утилит, репозиториев и знания форматов. При этом неизменившиеся файлы
между снимками — это один и тот же inode, и место они занимают один раз.

Проверено на практике: три ежедневных снимка источника с файлом 2 МБ, из
которых менялся только текстовый конфиг, заняли 2 МБ, а не 6 МБ.

Дополнительно можно включить `borg` — он даст сжатие, дедупликацию на уровне
блоков и шифрование поверх снимков:

```yaml
backup_engine: "borg"
backup_borg_passphrase: "{{ vault_backup_borg_passphrase }}"
```

Ключ репозитория выгружается в `/var/lib/nekta-backup/borg-key-*.txt`.
**Скопируйте его в место хранения вне сервера копий**: без ключа и ключевой
фразы репозиторий не открыть.

## Глубина хранения

Схема дед-отец-сын, значения по умолчанию:

```yaml
backup_keep_daily: 14     # последние 14 суток
backup_keep_weekly: 8     # по одному снимку на каждую из 8 недель
backup_keep_monthly: 12   # по одному на каждый из 12 месяцев
```

Итого около 34 снимков, покрывающих год. Глубина хранения самих **данных** в
Nekta задаётся отдельно, в настройках приложения, и на ротацию копий не
влияет.

## Расписание и защита от переполнения

Копирование запускает systemd-таймер `nekta-backup.timer` (по умолчанию 01:30
со случайной задержкой до 15 минут). Перед стартом проверяется свободное
место: при остатке меньше `backup_min_free_percent` (15%) цикл не запускается
и уходит письмо. Заполнить том целиком копия не может — это привело бы к
потере и новых копий, и возможности удалить старые.

Параллельные запуски исключены блокировкой: одновременная работа двух циклов
испортила бы `--link-dest` и ротацию.

## Контроль: копия, о которой не знают, что она не снимается

Ежедневно в 09:00 таймер `nekta-backup-check.timer` проверяет свежесть копий
и присылает письмо, если последняя успешная старше `backup_max_age_hours`
(30 часов) или на томе кончается место.

```bash
nekta-backup-status          # человекочитаемый отчёт, код возврата 0/1
```

Код возврата удобно опрашивать внешним мониторингом. Состояние по каждому
источнику лежит в `/var/lib/nekta-backup/status-<источник>.json`.

Неудавшийся снимок сохраняется как `FAILED-<дата>` и **не становится** базой
для следующего `--link-dest`, чтобы неполные данные не размножились по всей
цепочке снимков.

## Ручной запуск

```bash
ansible-playbook playbooks/backup-run.yml
ansible-playbook playbooks/backup-run.yml -e backup_dry_run=true

# на самом сервере копий
nekta-backup
nekta-backup --source nekta-01
nekta-backup --dry-run
```

Журналы — `/var/log/nekta-backup/backup-<дата>.log` и `journalctl -t nekta-backup`.

## Восстановление

### Просмотр и выборочное восстановление

```bash
nekta-restore list                       # все источники
nekta-restore list nekta-01
nekta-restore info nekta-01 2026-09-01_013000

# распаковать в локальный каталог
nekta-restore extract nekta-01 2026-09-01_013000 /nekta/backup-dumps/latest /tmp/dump

# вернуть на сервер: без --apply идёт проверочный прогон
nekta-restore push nekta-01 2026-09-01_013000 /etc/nekta nekta-01:/etc/nekta
nekta-restore push nekta-01 2026-09-01_013000 /etc/nekta nekta-01:/etc/nekta --apply
```

Снимки — обычные файлы, поэтому `nekta-restore` не обязателен: `cp`, `rsync`
и `tar` работают с ними напрямую.

### Восстановление базы данных

Файлы БД из снимка — это состояние на момент копирования работающей системы.
Восстанавливайте **из дампа**, который снял `nekta-predump`:

```bash
# 1. Достать дамп нужной даты
nekta-restore extract nekta-01 2026-09-01_013000 /nekta/backup-dumps /tmp/restore

# 2. Найти дамп кластера
ls /tmp/restore/backup-dumps/*/db/

# 3. Залить в контейнер (пример для PostgreSQL)
gunzip -c /tmp/restore/backup-dumps/2026-09-01_004500/db/postgres_<контейнер>.sql.gz \
  | docker exec -i <контейнер> psql -U postgres
```

Точные имена контейнеров и порядок остановки стека уточняйте у техподдержки
Nekta: состав стека — зона ответственности вендора.

### Восстановление сервера целиком

1. Установить ОС той же версии, разметить диски (`playbooks/site.yml --tags storage`).
2. Восстановить `/nekta` и `/etc` из снимка на новый сервер.
3. Передать вендору доступ для установки стека Nekta
   ([06-handover.md](06-handover.md)); состав контейнеров и образов есть в
   снимке — `backup-dumps/*/system/docker-ps.txt` и `docker-images.txt`.
4. После установки стека залить дампы БД.

## Проверяйте восстановление, а не копирование

Успешный `nekta-backup-status` говорит, что файлы скопировались, но не что из
них можно восстановиться. Раз в квартал стоит выполнять учебное
восстановление на отдельной машине:

```bash
nekta-restore extract nekta-01 <снимок> /nekta/backup-dumps /tmp/drill
gunzip -t /tmp/drill/backup-dumps/*/db/*.gz    # целостность архивов
```

Это единственный способ заранее узнать, что дамп пустой или бьётся —
до того, как он понадобится всерьёз.
